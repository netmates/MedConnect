# MedConnect

## Сайт для записи к врачу и общения с ним

Версия: 1.0
Статус: Draft
Команда: 2 разработчика
Тип проекта: учебный MVP для курсовой работы
Технологический стек: ASP.NET Core, React.js или Blazor, PostgreSQL, MongoDB, Redis, RabbitMQ/Kafka, Docker/Kubernetes, gRPC, SignalR, OpenTelemetry

---

# 1. Обзор продукта

MedConnect — веб-платформа для онлайн-записи пациентов к врачам и последующего общения с ними через встроенный чат.

Система позволяет пациенту найти врача, посмотреть доступные слоты, записаться на приём, отменить или перенести запись, а также отправить врачу сообщение после создания записи.

Для врача система предоставляет возможность управлять своим расписанием, просматривать записи пациентов и вести коммуникацию с пациентами.

Проект разрабатывается как учебный MVP, поэтому не претендует на полноценную медицинскую информационную систему. В MVP не хранятся реальные медицинские диагнозы, результаты анализов, рецепты и полноценные медицинские карты.

Основной акцент проекта — не только пользовательская функциональность, но и демонстрация современной backend-инфраструктуры: микросервисы, брокер сообщений, NoSQL, gRPC, SignalR, Redis, структурное логирование, мониторинг и контейнеризация.

---

# 2. Проблема

Пациенту часто неудобно записываться к врачу вручную: через звонки, мессенджеры или разрозненные сайты клиник. После записи коммуникация с врачом также часто происходит вне единой системы.

Врачам и администраторам сложно поддерживать актуальное расписание, отслеживать отмены, новые записи и сообщения пациентов.

Для учебного проекта эта предметная область удобна тем, что позволяет естественно применить микросервисную архитектуру:

* отдельный сервис расписания и записей;
* отдельный сервис коммуникации;
* отдельный сервис уведомлений;
* событийное взаимодействие через брокер сообщений;
* хранение сообщений в NoSQL;
* real-time коммуникация через SignalR;
* gRPC для внутреннего взаимодействия сервисов.

# 3. Цели проекта

## 3.1. Продуктовые цели

1. Дать пациенту возможность записаться к врачу онлайн.
2. Дать врачу возможность управлять доступными временными слотами.
3. Позволить пациенту и врачу общаться внутри системы.
4. Отправлять системные уведомления о создании, отмене и изменении записи.

6. Реализовать Swagger/OpenAPI-документацию.
7. Добавить CI pipeline с запуском тестов.
8. Реализовать один из вариантов: gRPC, SignalR или GraphQL.
9. Добавить структурное логирование.
10. Добавить Redis-кеширование.
11. Добавить middleware.
12. Добавить FluentValidation.
13. Продемонстрировать мониторинг и трассировку.

# 4. Целевая аудитория

## 4.1. Пациент

Пользователь, который хочет записаться к врачу, посмотреть свои записи и отправить врачу сообщение.

Основные задачи:

* найти врача;
* посмотреть доступные слоты;
* записаться на приём;
* отменить запись;
* написать врачу сообщение;
* получить уведомление о записи.

## 4.2. Врач

Пользователь, который принимает пациентов и управляет своим расписанием.

Основные задачи:

* создать доступные слоты для записи;
* просмотреть список будущих приёмов;
* отменить или подтвердить запись;
* ответить пациенту в чате.

## 4.3. Администратор

Пользователь с расширенными правами.

В MVP роль администратора можно реализовать частично.

Основные задачи:

* управлять списком врачей;
* управлять специализациями;
* просматривать общую информацию по записям.

# 5. Роли пользователей

1. Guest — неавторизованный пользователь.
2. Patient — пациент.
3. Doctor — врач.
4. Admin — администратор.

Авторизация может быть реализована через Keycloak или через собственный Auth Service, если команда решит упростить инфраструктуру.

Для курсового проекта предпочтительно использовать Keycloak, так как это добавляет инфраструктурную ценность и показывает работу с внешним Identity Provider.

# 8. Пользовательские сценарии

## 8.1. Запись пациента к врачу

1. Пациент входит в систему.
2. Открывает список врачей.
3. Выбирает специализацию.
4. Открывает карточку врача.
5. Видит доступные слоты.
6. Выбирает слот.
7. Подтверждает запись.
8. Система создаёт appointment.
9. Система публикует событие `AppointmentCreated`.
10. Notification Service получает событие.
11. Notification Service логирует уведомление.
12. Пациент видит запись в личном кабинете.

## 8.2. Отмена записи пациентом

1. Пациент открывает список своих записей.
2. Выбирает будущую запись.
3. Нажимает «Отменить».
4. Система меняет статус записи на `Cancelled`.
5. Система освобождает слот.
6. Система публикует событие `AppointmentCancelled`.
7. Notification Service обрабатывает событие.
8. Врач видит обновлённый статус записи.

## 8.3. Создание слотов врачом

1. Врач входит в систему.
2. Открывает раздел «Моё расписание».
3. Выбирает дату и время.
4. Создаёт доступный слот.
5. Слот становится доступен пациентам для записи.

## 8.4. Общение пациента с врачом

1. Пациент открывает свою запись.
2. Переходит в чат с врачом.
3. Отправляет сообщение.
4. Communication Service сохраняет сообщение в MongoDB.
5. Сообщение доставляется врачу через SignalR.
6. Врач отвечает пациенту.
7. История сообщений сохраняется в MongoDB.

# 9. Функциональные требования

## 9.1. Управление врачами

Система должна позволять:

1. Создавать профиль врача.
2. Просматривать список врачей.
3. Просматривать карточку врача.
4. Назначать врачу специализацию.
5. Искать врачей по специализации.

Поля врача:

* ID;
* ФИО;
* специализация;
* описание;
* стаж;
* статус активности.

---

## 9.2. Управление специализациями

Система должна позволять:

1. Создавать специализацию.
2. Получать список специализаций.
3. Привязывать специализацию к врачу.

Примеры специализаций:

* терапевт;
* кардиолог;
* невролог;
* педиатр;
* дерматолог.

---

## 9.3. Управление расписанием

Система должна позволять врачу:

1. Создавать временные слоты.
2. Просматривать свои слоты.
3. Отменять свободные слоты.
4. Видеть занятые слоты.

Слот может иметь статусы:

* Available;
* Booked;
* Cancelled.

Поля слота:

* ID;
* DoctorId;
* StartTime;
* EndTime;
* Status;
* CreatedAt;
* UpdatedAt.

---

## 9.4. Управление записями

Система должна позволять пациенту:

1. Создавать запись на свободный слот.
2. Просматривать свои записи.
3. Отменять будущую запись.

Система должна позволять врачу:

1. Просматривать записи к себе.
2. Отменять запись.

Запись может иметь статусы:

* Created;
* Confirmed;
* Cancelled;
* Completed.

В MVP статус `Completed` может выставляться вручную или не использоваться в интерфейсе.

Поля записи:

* ID;
* PatientId;
* DoctorId;
* SlotId;
* Status;
* Reason;
* CreatedAt;
* UpdatedAt.

---

## 9.5. Чат пациента и врача

Система должна позволять:

1. Создавать чат для записи.
2. Отправлять сообщения.
3. Получать историю сообщений.
4. Доставлять новые сообщения в real-time через SignalR.

Ограничение MVP:

* чат доступен только для пациента и врача, связанных конкретной записью;
* файлы и вложения не поддерживаются;
* статусы прочтения можно не реализовывать.

Поля сообщения:

* ID;
* ChatId;
* AppointmentId;
* SenderId;
* SenderRole;
* Text;
* CreatedAt.

---

## 9.6. Уведомления

Notification Service должен обрабатывать события:

1. `AppointmentCreated`;
2. `AppointmentCancelled`;
3. `MessageCreated`.

В MVP уведомления не отправляются реально, а логируются в структурированном виде.

Пример логируемого уведомления:

```json
{
  "event": "AppointmentCreated",
  "patientId": "uuid",
  "doctorId": "uuid",
  "appointmentId": "uuid",
  "createdAt": "2026-07-03T10:00:00Z"
}
```

# 10. Нефункциональные требования

## 10.1. Производительность

1. Список врачей должен открываться менее чем за 1 секунду при тестовом объёме данных.
2. Создание записи должно выполняться менее чем за 2 секунды.
3. Отправка сообщения должна визуально отображаться у получателя почти мгновенно через SignalR.

## 10.2. Надёжность

1. При создании записи должна быть защита от двойного бронирования одного слота.
2. События должны публиковаться после успешного изменения состояния.
3. Ошибки должны логироваться со структурированным контекстом.
4. Сервисы должны иметь health checks.

## 10.3. Безопасность

1. Доступ к API должен быть защищён JWT-токенами.
2. Пациент может видеть только свои записи.
3. Врач может видеть только свои записи.
4. Чат доступен только участникам соответствующей записи.
5. Административные операции доступны только пользователю с ролью Admin.
6. В MVP запрещается использовать реальные медицинские данные.

## 10.4. Наблюдаемость

1. Все сервисы должны писать структурированные логи.
2. Все входящие HTTP-запросы должны иметь CorrelationId.
3. Метрики сервисов должны быть доступны для Prometheus.
4. Трейсы должны экспортироваться через OpenTelemetry.
5. Для визуализации можно использовать Grafana.

* ASP.NET Core;
* YARP или собственный BFF;

Основной сервис бизнес-логики записи к врачу.

Отвечает за:

* врачей;
* специализации;
* расписание;
* слоты;
* записи пациентов.

База данных:

* PostgreSQL.

Технологии:

* ASP.NET Core Web API;
* EF Core;
* FluentValidation;
* PostgreSQL;
* Redis;
* RabbitMQ/Kafka producer;
* gRPC client/server.

---

### 3. Communication Service

Сервис общения пациента и врача.

Отвечает за:

* чаты;
* сообщения;
* историю сообщений;
* real-time доставку сообщений.

База данных:

* MongoDB.

Технологии:

* ASP.NET Core;
* MongoDB Driver;
* SignalR;
* RabbitMQ/Kafka producer;
* Swagger.

---

### 4. Notification Service

Сервис обработки событий и уведомлений.

Отвечает за:

* получение событий из брокера;

* логирование уведомлений;

База данных:

* можно не использовать;
* либо использовать MongoDB/PostgreSQL для хранения истории уведомлений.

Технологии:

* ASP.NET Core Worker Service;
* RabbitMQ/Kafka consumer;
* Serilog;
* OpenTelemetry.

### 5. Identity Provider

Для авторизации можно использовать Keycloak.

Отвечает за:

* пользователей;
* роли;
* JWT-токены;
* авторизацию пациентов, врачей и администраторов.

Технологии:

* Keycloak;
* PostgreSQL для Keycloak при необходимости.

# 12. Взаимодействие сервисов

## 12.1. HTTP

Frontend обращается к API Gateway/BFF по HTTP.

API Gateway/BFF обращается к сервисам:

* Appointment Service;
* Communication Service.

---

## 12.2. gRPC

gRPC можно использовать для внутреннего взаимодействия между сервисами.

Рекомендуемый сценарий:

Communication Service перед созданием чата или отправкой сообщения обращается в Appointment Service по gRPC, чтобы проверить, что пациент и врач действительно связаны записью.

Пример метода:

```proto
service AppointmentGrpcService {
  rpc ValidateAppointmentAccess(ValidateAppointmentAccessRequest)
      returns (ValidateAppointmentAccessResponse);
}
```

Пример проверки:

* существует ли appointment;
* принадлежит ли PatientId этой записи;
* принадлежит ли DoctorId этой записи;
* не отменена ли запись.

---

## 12.3. Брокер сообщений

Брокер используется для асинхронных событий:

* AppointmentCreated;
* AppointmentCancelled;
* MessageCreated.

Producer:

* Appointment Service;
* Communication Service.

Consumer:

* Notification Service.

Рекомендуемый брокер для MVP:

* RabbitMQ — проще для учебного проекта;
* Kafka — интереснее инфраструктурно, но сложнее.

Для команды из 2 человек рекомендуется RabbitMQ.

# 13. Хранилища данных

## 13.1. PostgreSQL

Используется в Appointment Service.

Сущности:

* Doctors;
* Specializations;
* DoctorSpecializations;
* ScheduleSlots;
* Appointments.

Используется EF Core.

---

## 13.2. MongoDB

Используется в Communication Service.

Коллекции:

* Chats;
* Messages.

Причина выбора NoSQL:

* сообщения имеют документную структуру;
* история чата естественно хранится в виде документов;
* можно быстро получать сообщения по ChatId;
* это закрывает требование курсовой по NoSQL.

---

## 13.3. Redis

Используется для кеширования:

* списка специализаций;
* карточек врачей;
* доступных слотов врача на ближайшие дни.

Также Redis можно использовать для SignalR backplane, если будет несколько экземпляров Communication Service.

# 16. Валидация

Валидация должна быть реализована через FluentValidation.

Примеры правил:

## 16.1. Создание слота

1. StartTime должен быть больше текущего времени.
2. EndTime должен быть больше StartTime.
3. Длительность слота должна быть от 15 до 120 минут.
4. У врача не должно быть пересекающихся слотов.

## 16.2. Создание записи

1. SlotId обязателен.
2. Reason не должен превышать 500 символов.
3. Слот должен существовать.
4. Слот должен быть свободен.
5. Пациент не может записаться на один и тот же слот дважды.

## 16.3. Отправка сообщения

1. Text обязателен.
2. Text не должен превышать 2000 символов.
3. Пользователь должен быть участником чата.

# 17. Middleware

В проекте должен быть реализован custom middleware.

Рекомендуемый вариант:

## CorrelationIdMiddleware

Назначение:

* проверять наличие заголовка `X-Correlation-Id`;
* если заголовка нет — генерировать новый CorrelationId;
* добавлять CorrelationId в response headers;
* помещать CorrelationId в лог-контекст;
* прокидывать CorrelationId между сервисами.

Пример заголовка:

```http
X-Correlation-Id: 6f1b7b8a-3b4d-4e11-a84f-91e49c7c07d1
```

# 18. Нестандартный DI

Для демонстрации нестандартного DI можно реализовать модульную регистрацию зависимостей.

Пример подхода:

```csharp
public interface IServiceModule
{
    void Register(IServiceCollection services, IConfiguration configuration);
}
```

Каждый слой или модуль регистрирует свои зависимости через отдельный класс:

```csharp
public sealed class AppointmentModule : IServiceModule
{
    public void Register(IServiceCollection services, IConfiguration configuration)
    {
        services.AddScoped<IAppointmentService, AppointmentService>();
        services.AddScoped<IAppointmentRepository, AppointmentRepository>();
    }
}
```

Дополнительно можно использовать:

* Scrutor для автоматической регистрации сервисов;
* keyed services для выбора стратегии уведомлений;
* decorator для логирования обработчиков команд.

Пример стратегий уведомлений:

* EmailNotificationSender;
* SmsNotificationSender;
* FakeNotificationSender.

В MVP реально используется FakeNotificationSender, остальные реализации нужны для демонстрации расширяемости.

# 27. Риски

## 27.1. Риск переусложнения

Проект может стать слишком большим для 2 человек.

Митигация:

* сначала сделать Appointment Service;
* затем Communication Service;
* Notification Service делать максимально простым;
* Admin UI оставить минимальным.

## 27.2. Риск сложности Keycloak

Keycloak может занять много времени.

Митигация:

* сначала реализовать упрощённую авторизацию;
* Keycloak подключить после стабилизации основных сценариев;
* для защиты подготовить заранее тестовых пользователей.

## 27.3. Риск сложности Kubernetes

Production-like Kubernetes может занять слишком много времени.

Митигация:

* основной запуск делать через Docker Compose;
* Kubernetes manifests подготовить для демонстрации;
* не усложнять Helm, Ingress и TLS на первом этапе.

## 27.4. Риск сложности real-time чата

SignalR может потребовать дополнительной настройки.

Митигация:

* сначала сделать обычное REST API для сообщений;
* затем добавить SignalR;
* Redis backplane делать только если останется время.

# 28. Итоговая рекомендация

Тема «Сайт для записи к врачу и общения с ним» хорошо подходит для курсовой работы, потому что она:

1. Понятна комиссии и легко демонстрируется.
2. Естественно раскладывается на микросервисы.
3. Позволяет использовать PostgreSQL, MongoDB и Redis.
4. Хорошо подходит для брокера сообщений.
5. Даёт уместный сценарий для SignalR.
6. Даёт уместный сценарий для gRPC.
7. Позволяет показать мониторинг, логи и трассировку.
8. Может быть разумно ограничена до MVP.

Главное — не пытаться делать полноценную медицинскую систему. Для защиты лучше сфокусироваться на одном сильном end-to-end сценарии:

пациент выбирает врача → записывается на слот → событие уходит в брокер → уведомление логируется → пациент и врач общаются в чате → всё видно в логах, Swagger, MongoDB, RabbitMQ и Grafana.
